# Deriv Higher/Lower Bot

Automated 10-tick Higher/Lower trading bot for Deriv's R_25 (Volatility 25) synthetic index, with a live monitoring dashboard.

## Strategy: volatility-timing, not direction

This bot fires on a **volatility-percentile timing signal**, not a directional (chart-pattern) one. That's a deliberate change from an earlier EMA9/EMA21 + momentum version — extensive backtesting (384 pullback-pattern combinations, a 5-feature logistic regression, a 6-signal conviction ensemble, autocorrelation/variance-ratio/runs tests, and an RNG periodicity check, all detailed in the accompanying backtest report) found no exploitable directional edge on this instrument, consistent with Deriv's own description of synthetic indices as generated by a cryptographically secure RNG.

What *is* real and backtested: tick-return **magnitude** clusters in time even though direction doesn't (autocorrelation of `|return|` ~0.013 at lags 1–50 for R_25). This bot trades that:

1. On every tick, a rolling realized-volatility estimate (`VOL_WINDOW_TICKS`, default 100) is updated.
2. Once per UTC day, a threshold is computed as the `VOL_TARGET_PERCENTILE`th percentile (default 90th = "top 10%") of the trailing `VOL_TRAILING_DAYS` (default 90) days of volatility samples — using only *prior* days, never the current one, matching the non-lookahead backtest.
3. When current rolling volatility is at or above that threshold, a signal fires — always in the fixed `BET_DIRECTION` (default `LOWER`; direction has no backtested edge either way, so this only needs to be *a* consistent choice).
4. A qualifying signal opens **one** genuine Higher/Lower contract (`contract_type: HIGHER`/`LOWER` — not Rise/Fall), duration `CONTRACT_DURATION_TICKS` (default 10 ticks), barrier a **fixed** signed offset (`BARRIER`, default 0.30 — not ATR-derived).
5. Only one contract is ever open at a time (matching the non-overlapping-trades assumption the backtest used) — a new signal is not evaluated while one is settling.
6. The contract is polled until settlement; results and PnL persist to the database.

### Honest performance note

At the live quoted payout for R_25 barrier 0.30 ($3.00 back per $1 staked → breakeven win rate 33.33%), the validated, out-of-sample, non-lookahead win rate for this exact configuration was **31.9–32.0%** — short of breakeven by roughly **1.0–1.6 percentage points**. This is the closest to breakeven found across an extensive search; it is **not known to be profitable**. See the accompanying backtest report (Sections 5, 7, and 11–12) for the full numbers, methodology, and everything that was ruled out along the way. Nothing in this codebase or dashboard should be read as a claim that this strategy wins on average.

### What to verify before trading this live

- **Tick-duration Higher/Lower contracts for this account/symbol are not yet confirmed.** This account's own `contracts_for` check (2026-07-24) found an "intraday" (15s–1d) duration tier for R_25's `higherlower` category, but that check pre-dates this bot's move to tick-duration contracts (2026-07-29) and did not specifically confirm a `duration_unit: "t"` tier. Run `/api/diagnostics/contracts-for` after connecting and check the response before enabling `AUTO_TRADE=true` in live mode. If tick duration isn't offered, `proposal()` will fail loudly (a `DerivAPIError`) rather than silently substituting a different duration.
- **The 90-day trailing volatility history is not backfilled from Deriv on first deploy** (see `engine.py`'s `VolatilityTracker.bootstrap()` docstring for why — it needs paginating `ticks_history` in a way that depends on this account's actual rate limits, which this project's development environment had no way to verify against the live API). A brand-new deployment accumulates its own trailing history over `VOL_TRAILING_DAYS` of uptime and **will not fire any signals until then** (`current_vol_threshold` in `/api/status` stays `null`) — this is a deliberate fail-safe, not a bug.

## Configuration

Set via `.env` locally, or Fly secrets / `fly.toml` `[env]` in production.

| Variable | Default | Purpose |
|---|---|---|
| `DERIV_APP_ID` / `DERIV_PAT` | — | PAT authentication (required) |
| `DERIV_ACCOUNT_ID` | — | Optional: pin a specific account instead of auto-selecting by mode |
| `BOT_MODE` | `demo` | Fallback default only — overridden by the Settings page toggle once used, which persists across restarts |
| `MARKET_SYMBOL` | `R_25` | Symbol to trade |
| `STAKE` | `1.0` | Stake per trade |
| `CURRENCY` | `USD` | Account currency |
| `AUTO_TRADE` | `true` | Execute qualifying signals automatically |
| `CONTRACT_DURATION_TICKS` | `10` | Contract duration in ticks — this is what was backtested; changing it means trading an unvalidated variant |
| `BARRIER` | `0.30` | Fixed, signed-offset barrier magnitude (not ATR-derived) |
| `BET_DIRECTION` | `LOWER` | `HIGHER` or `LOWER` — fixed for every signal (no directional edge found; see report) |
| `VOL_WINDOW_TICKS` | `100` | Rolling window (in ticks) for the realized-volatility estimate |
| `VOL_TRAILING_DAYS` | `90` | How many preceding days feed the percentile threshold |
| `VOL_TARGET_PERCENTILE` | `90.0` | Signal fires when current volatility is at/above this percentile of its trailing history |
| `DATABASE_URL` | `sqlite+aiosqlite:///./data/bot.db` | SQLite by default; any Postgres-compatible URL also works |

```bash
cp .env.example .env
docker compose up --build
```

## Fly.io deployment

```bash
fly secrets set DERIV_APP_ID="..." DERIV_PAT="..." -a crypto-signal-bot-kooj9a
fly deploy -a crypto-signal-bot-kooj9a
```

**Persistent storage — one-time setup.** The SQLite database lives on a Fly Volume mounted at `/app/data` (`fly.toml`). The volume must exist before it can be mounted:
```bash
fly volumes create bot_data --region ams --size 1 -a crypto-signal-bot-kooj9a
```
Skip this and every redeploy runs on a fresh machine with an empty database.

Health check: `curl https://YOUR_APP.fly.dev/health`.

## Dashboard

- **Dashboard** — bot status, current signal, today's PnL/win-rate/wins/losses, a ring showing current rolling volatility relative to the trailing-percentile threshold.
- **Signals** / **Trades** — history with color-coded status badges (qualified/executed/error, won/lost/pending), including the volatility reading and threshold each signal fired on.
- **P&L** — cumulative PnL chart and daily breakdown.
- **Settings** — Demo/Live toggle (saves automatically, restarts the bot to apply), the fixed barrier/direction/volatility-filter settings, and two diagnostics tools: a copyable activity/error summary (`/api/diagnostics`), and a live query of Deriv's own contract specs for this symbol (`/api/diagnostics/contracts-for`).

## Architecture

- `backend/app/deriv.py` — Deriv API client: separate public (market data) and trade (authenticated) WebSockets, PAT + OTP auth, structured error handling, reconnect/backoff, tick-duration proposals, and raw tick-history fetching for volatility bootstrap.
- `backend/app/strategy.py` — `RollingVolatility` (incremental rolling std of tick deltas) and `VolatilityTimingStrategy` (pure, stateless decision function: given a current volatility reading and threshold, fire or don't).
- `backend/app/engine.py` — `VolatilityTracker` (owns the rolling window, the persisted trailing-day sample history, and the daily percentile threshold) plus `BotEngine` (tick loop, signal → execution → settlement lifecycle, non-overlapping-trade enforcement, connection health monitoring, resume-open-trades-after-restart).
- `backend/app/api.py` / `main.py` — FastAPI app, dashboard API, static asset serving (cache-busted by build version so a redeploy can't leave a browser on stale JS/CSS).
- `backend/app/db.py` — SQLAlchemy models (`Signal`, `Trade`, `BotEvent`, `RuntimeSetting`, `VolSample`) with lightweight additive migrations for existing databases.
- `frontend/` — vanilla HTML/CSS/JS dashboard, no build step, served directly by FastAPI.
